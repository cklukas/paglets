# paglets/cpp: communication, system paglets and access control

Status: draft design, companion to [cpp-edition-plan.md](cpp-edition-plan.md).

This document designs how paglets talk to each other, how the mesh locates
them, and how roaming paglets get controlled access to host resources. The
model has three parts:

- **Capabilities**: a paglet can only reach another paglet or a host resource
  through an unforgeable handle it has been given.
- **System paglets**: privileged, platform-independent host services (files,
  system information, load, volumes, ...) that roaming paglets use through
  service methods or explicit grants.
- **Mesh governance**: all security decisions belong to the mesh, not to
  individual hosts. They are made by **mesh admins**, who are identified by
  their keys and can act from any live host. Every host enforces the same
  signed, replicated security state.

## 1. Principles

1. **No ambient authority.** A roaming paglet starts with almost nothing: its
   own identity, a few default handles, and whatever its creator passes in.
   There is no direct file, network or OS access and no way to message a
   paglet it holds no handle for.
2. **Capabilities, not access lists.** Holding a handle is the permission.
   Handles live in a host-side table per paglet; the guest only sees small
   integers and cannot forge or guess them.
3. **Hosts mediate, the mesh decides.** Every message, grant and privileged
   operation passes through the local host, which checks it against the mesh
   security state. No host decides security questions on its own authority.
4. **Admins are keys, not machines.** Mesh admin authority comes from admin
   signing keys. An admin can approve, deny, grant and revoke from any live
   host; no host is special and no admin needs to log into a particular host.
5. **Least privilege by default.** Grants are narrow (operations, named roots,
   paths), time-limited, revocable and audited.
6. **One interface for native and Wasm providers.** A caller cannot tell
   whether a service is implemented natively in the host or by a trusted Wasm
   system paglet.
7. **All hosts are equal.** There is no central, coordinating, hub or home
   host for anything: security state, location, relaying, discovery and
   scheduling are all spread over the hosts with identical roles. Any host can
   fail without taking a mesh function down with it.

## 2. Meshes, hosts and paglet kinds

A **mesh** is a defined set of hosts that share one security state. A host
belongs to exactly one mesh. Paglets move freely between hosts of their mesh;
moving between meshes is not supported in release 1.

All hosts of a mesh run the same software with the same system paglets and
the same roles. Hosts differ only in their labels, named roots and resources,
never in authority. Where a function needs specific hosts (for example who
stores a paglet's location record), they are chosen deterministically from the
enrolled host set, so the choice spreads evenly and moves automatically when
hosts join, leave or fail.

Every paglet has a trust class. The host assigns it; a paglet never claims its
own class, and an arriving paglet is always `roaming`.

| Kind | Origin | Moves | Import set | Examples |
|---|---|---|---|---|
| **System paglet** | Built into the host (native C++) or a Wasm module trusted by the mesh ledger | Never | Standard + privileged host API | files, server-info, grants, directory, locator |
| **Resident paglet** | Application paglet the mesh admins assign to a host | No (stays on its host) | Standard | A site-specific collector or gateway |
| **Roaming paglet** | Created by an owner or another paglet, or arrived from another host | Yes | Standard only | Compute jobs, search agents, file grabbers |

## 3. Identity and the mesh security ledger

### 3.1 Keys, authentication and encryption

paglets/cpp uses **public-key cryptography only**. There are no shared
passwords or API keys, and no secret ever travels over the network: peers
exchange public keys and signatures, and private keys never leave the machine
that generated them. The shared `PAGLETS_API_KEY` of the Python edition has no
equivalent.

All identities are Ed25519 key pairs:

| Key | Generated by | Private key stored | Public key known through |
|---|---|---|---|
| **Admin key** | `paglets keys init --admin` on the admin's own machine | Admin's machine only, never on hosts | Genesis record or admin set change |
| **Host key** | The host at installation | That host only | Host enrollment record |
| **Owner key** | `paglets keys init` on the owner's machine | Owner's machine only | Owner enrollment record |

Protecting private keys:

- Admin and owner keys are stored encrypted. The key-encryption key is derived
  from a local passphrase with Argon2id; the passphrase is only ever typed and
  used locally, never sent anywhere.
- Host keys are stored with owner-only file permissions, or in the platform key
  store where available (macOS Keychain, Windows DPAPI/CNG).
- A local key agent (like `ssh-agent`) can hold unlocked admin or owner keys
  for a session, so the CLI signs without asking for the passphrase each time.
  Hardware keys (FIDO2 / PIV tokens) are a later option; the ledger only needs
  public keys and signatures, so nothing else changes.
- Keys are rotated and revoked through ledger records; a lost or stolen key is
  removed by an admin set change (admin keys) or a revocation (host and owner
  keys).

Authentication, always by signature over a fresh challenge:

- **CLI to host**: the host sends a random challenge; the CLI signs it with the
  admin or owner key; the host checks the signature against the ledger. No
  password or token is transmitted.
- **Admin decisions** are additionally signed records in their own right, so
  they stay verifiable by every host after gossip, independent of the session
  they arrived through.
- **Host to host**: both hosts prove possession of their enrolled host keys
  during the channel handshake.

Encryption in transit, in two layers:

1. **Transport**: all HTTP traffic uses HTTPS (TLS 1.3). This keeps corporate
   reverse proxies and firewalls working, but TLS may be terminated by a proxy
   or by a peer that relays for a host without inbound ports.
2. **End-to-end channels**: on top of the transport, every host pair and every
   CLI session runs an authenticated key exchange (a Noise-style handshake
   using the X25519 forms of the Ed25519 identity keys, with forward secrecy)
   and encrypts all frames with ChaCha20-Poly1305. Reverse proxies and relaying
   peers forward ciphertext only; they cannot read or alter messages, images,
   modules or ledger records.

At rest: memory images, the ledger and artifacts are stored on the hosts that
hold them. Encrypting images at rest with a host-held key is an option for a
later release; a host that runs a paglet must be able to read its memory
anyway.

### 3.2 The ledger

The mesh security state is a **ledger**: an append-only set of signed records,
replicated to every host by gossip. Every host keeps a full copy, verifies
every signature, and derives the same current state from it. Because any host
can accept and serve records, there is no central security host.

The ledger starts with a **genesis record** created by `paglets mesh create`:
the mesh ID, the initial admin public keys and the quorum rules, signed by
those admins. Hosts are installed with the mesh ID and the genesis hash as
their trust anchor.

Record types:

| Record | Signed by | Content |
|---|---|---|
| Admin set change | Quorum of current admins | Add, remove or rotate admin keys; change quorum rules |
| Host enrollment / removal | Admin | Host key, name, labels (for example `linux`, `gpu`, `lab-a`), named roots |
| Owner enrollment / removal | Admin | Owner key, display name, groups |
| Module trust | Admin | Trusted module signer keys and module hash allowlist |
| Policy rule | Admin | Rule ID, match conditions, decision, scope, limits (section 7) |
| Grant | Admin, or derived from an `allow` rule | Subject, resource, host selector, expiry |
| Revocation | Admin | Revokes a grant, enrollment or module trust |
| Request | Host (on behalf of a paglet or a new host/owner) | Pending grant or enrollment request |
| Checkpoint | Admin | Compacted state snapshot so old records can be pruned |

State rules:

- Records are ordered by a logical clock and the signer key, so every host
  computes the same state from the same set of records.
- Revocations always win over grants, regardless of order.
- Records signed by a removed admin after their removal are ignored.
- The default quorum is one admin signature for normal operations. Changes to
  the admin set can require more (for example 2 of 3), configured in genesis.

### 3.3 Acting as an admin

An admin runs the `paglets admin ...` CLI on their own machine. The CLI connects
to **any live host** of the mesh, shows pending requests and current state from
that host's ledger copy, signs decisions locally with the admin key, and
submits the signed records to that host, which gossips them to all others.

Examples: approve or deny a request, add a policy rule, enroll a host or owner,
trust a module signer, revoke a grant, force-release a pin.

### 3.4 Availability

- Hosts enforce the last ledger state they have. Allow and deny rules keep
  working while hosts are partitioned or admins are offline.
- Requests that need an admin decision (`ask`) wait as pending records until
  any admin approves or denies them from any host.
- After a partition heals, gossip merges the records and all hosts converge to
  the same state.

### 3.5 Paglet identity

Every paglet carries:

- **Paglet ID**: unique, stable across moves.
- **Module hash**: SHA-256 of its Wasm module.
- **Owner**: the enrolled owner key that launched it.
- **Passport**: a certificate signed by the owner key: owner, module hash, root
  paglet ID, declared capability manifest (section 7.2), expiry. Children and
  clones inherit the owner and carry a passport chain back to it. Hosts verify
  passports on creation and arrival.
- **Lineage**: parent ID, clone-of ID, origin host (informational only; the
  origin host has no special role for the paglet afterwards).

Every delivered message carries a **host-stamped sender record**: paglet ID,
owner, trust class, module hash and sending host. The receiver can rely on it
because only enrolled hosts construct it, and host-to-host channels are
mutually authenticated with enrolled host keys and encrypted end to end
(section 3.1).

## 4. Capabilities

### 4.1 Handle table

Each paglet has a host-side capability list. The guest refers to entries by
small integer handles. Kinds:

| Kind | Refers to |
|---|---|
| `endpoint` | A paglet or a service |
| `reply` | A one-shot reply channel for one request |
| `dir` / `file` | A directory subtree or a single file on a host |
| `artifact` | A content-addressed blob |
| `topic` | A publish/subscribe topic |
| `pin` | A pin lease on a paglet (section 5.3) |
| `timer` | A pending timer |

### 4.2 Endpoint rights

An endpoint capability records:

- target (paglet ID or service name),
- allowed operations (message names or service operations, `*` for all, plus
  the special rights `locate` and `pin`),
- badge: the grant it came from, delivered to the target with each message so
  services can apply scope and audit without an access list,
- expiry and optional use limit,
- `transferable` flag (may be passed on in messages).

### 4.3 Operations on capabilities

- **invoke**: send a message through it.
- **derive**: create a weaker copy (fewer operations, shorter expiry, fewer
  uses, not transferable). Rights can only shrink.
- **transfer**: attach it to a message; the host moves the entry into the
  receiver's table and rewrites the handle number.
- **drop**: release it.
- **inspect**: read its rights, expiry and target description.

### 4.4 How a paglet obtains capabilities

1. **At creation**: the creator receives an endpoint to the new paglet and can
   pass handles into it.
2. **In messages**: transferable handles attached by the sender.
3. **From the directory**: looking up a published name returns an endpoint if
   the mesh policy allows this principal to see it.
4. **From mesh grants**: the host materializes capabilities for every grant in
   the ledger that covers this paglet and this host (section 7).

### 4.5 Revocation

Every capability traces back to a grant, a creation event or a transfer.
Revoking a grant in the ledger invalidates all capabilities derived from it on
every host, as soon as the revocation record arrives there. Expiry works the
same way.

### 4.6 Capabilities and movement

Grants belong to the mesh, so they follow the paglet; host-local handles do
not.

| Capability | When the holder moves to another host |
|---|---|
| Endpoint to a paglet | Portable (paglet ID + rights; the mesh locates the target) |
| Endpoint to a service | Re-created on the target from the same mesh grant, bound to the target host's provider, if the grant's host selector covers the target |
| `dir` / `file` | Re-created on the target from the same mesh grant if the target has the named root; otherwise dropped. Open handles and mounts are closed before the snapshot |
| Reply capability | Portable until used |
| Artifact | Portable (content-addressed) |
| Topic | Portable (topics are mesh-wide) |
| Pin | Held pins stay valid; they refer to the pinned paglet, not to the holder's host |

On arrival the paglet receives an `arrived` event listing capabilities that
could not be re-created, so it can react or request more access.

## 5. Paglet-to-paglet communication and location

### 5.1 Messages

- Asynchronous: a message has a name, a MessagePack payload, optional attached
  capabilities and optional artifact references.
- Per-paglet mailbox with priorities and FIFO order within a priority; handlers
  run serially per paglet.
- **Request/reply**: a request automatically carries a one-shot reply
  capability and a correlation ID. The receiver can answer exactly once
  without gaining a general endpoint to the caller. Timeouts arrive as
  messages.
- Handlers never block; the guest SDK offers callbacks and continuation
  helpers for multi-step conversations.
- Quotas per sender and per receiver (queue length, bytes, messages per
  second) protect paglets from floods.
- Messages to a paglet that is moving are held by the sending host and
  delivered once the move completes.

### 5.2 Locating paglets

The mesh finds paglets dynamically; senders never need to know where a paglet
is.

- **Distributed location records**: each paglet's current location is stored
  on a small set of responsible hosts (for example 3), chosen by consistent
  hashing of the paglet ID over the enrolled, online hosts. No host is special:
  every host is responsible for an even share of paglets, and the share moves
  to other hosts automatically when hosts join, leave or fail.
- Every move commits by updating a majority of the responsible hosts. Each
  record carries a move counter, so a stale record never overwrites a newer
  one.
- Hosts cache recent locations. A host that no longer holds a paglet keeps a
  short-lived tombstone and answers with the new location.
- If the responsible hosts cannot answer (for example during a partition), the
  `locator` system paglet asks the mesh ("who holds paglet P?") and every host
  that holds P answers.
- `locator.locate(endpoint)` returns the current host and the time of the last
  move. It needs the `locate` right on the endpoint.

### 5.3 Locate and pin

A located paglet may move again right after it was found. To make "find it and
work with it there" reliable, the mesh supports pinning:

- `locator.locate_and_pin(endpoint, duration, reason)` locates the paglet and
  asks the host currently running it to pin it. The reply contains the host,
  a `pin` capability and the pin expiry.
- If the paglet moved in between, the host answers with a redirect and the
  locator follows it (bounded number of hops) until the pin succeeds or fails.
- While pinned, the paglet cannot leave its host: its own `dispatch` returns a
  `pinned` result with the earliest release time, and other dispatch requests
  are refused. Cloning, deactivation and message handling are unaffected.
- Pins are leases: they end at expiry or when the holder releases the `pin`
  capability. Several pins can be held at once; the paglet can move only after
  all have ended. Pins are persisted and survive a host restart.
- The `pin` right on the endpoint and the maximum pin duration come from mesh
  policy. Admins can force-release pins.
- Holders are not told when a pin ends early (an admin ended it); `release`
  then answers that the pin had ended (planning/cpp-location.md).

### 5.4 Discovery and groups

- The `directory` system paglet maps names to endpoints. Each published entry
  has a visibility rule (everyone, same owner, owner group, trust class).
- The `pubsub` system paglet provides mesh-wide topics. Publish and subscribe
  are separate rights.

## 6. System paglets and host services

### 6.1 Implementation forms

- **Native system paglets**: C++ classes compiled into the host that implement
  a `SystemPaglet` interface. Used for everything that touches the operating
  system.
- **Trusted Wasm system paglets**: Wasm modules trusted in the mesh ledger,
  given the privileged import set. Used for higher-level services that do not
  need direct OS access.
- Both expose service contracts with typed operations (message name, request
  and reply schema), exactly like application services.

### 6.2 Platform independence

Hosts run on macOS, Linux and Windows, so system paglets offer portable
operations rather than raw OS access (there is deliberately no command
execution service):

- **Named roots** instead of raw paths: the ledger maps root names per host,
  for example `shared-data` to `/data/shared` on Linux and `D:\Shared` on
  Windows. Paglets address files as root name plus a relative path with `/`
  separators.
- **Uniform results**: sizes in bytes, times in UTC, volumes and processes in
  the same schema on every platform, with an optional platform-specific detail
  field.
- A host platform layer implements each operation for macOS, Linux and
  Windows.

### 6.3 Standard system paglets

| Name | Purpose | Operations |
|---|---|---|
| `files` | File access within granted roots | find (name patterns, size/time filters), list, stat, read (whole or range), write, mkdir, move, delete, mount |
| `server-info` | System information | summary (OS, host name, CPU, memory, uptime), load (CPU, memory, per-core), volumes (drives/mount points, capacity, free space), processes (read-only list) |
| `directory` | Discover services and named paglets | lookup, publish, list |
| `locator` | Find and pin paglets | locate, locate_and_pin, release |
| `grants` | Access requests and grant status for paglets | request, status, release |
| `artifacts` | Blob store | put, get, stat |
| `storage` | Per-paglet persistent key/value and blob storage with quota | get, put, delete, list |
| `pubsub` | Mesh-wide topics | create, publish, subscribe |
| `user-info` | Notifications to the paglet's owner | notify |
| `mesh-info` | Mesh resource landscape, ranked targets | snapshot, rank |
| `compute-slots` | Slot scheduling for compute jobs | request, release, status |
| `ai` (where available) | Local AI inference (section 6.7) | capabilities, summarize, classify, extract, embed, generate, describe_image |
| `web` (where available) | Mediated web access from hosts allowed to reach the internet or specific sites (section 6.8) | capabilities, search, fetch, extract_text, download |

Most system paglets run on every host. Some, like `ai` and `web`, only run where
the host can provide the feature; they announce it as a service offer (6.6).

Paglets never get raw network sockets. Network access exists only as the
`web` system paglet on hosts that offer it.

### 6.4 Three levels of file access

1. **Service methods** (default): the paglet calls
   `files.find(dir_cap, "**/*.csv")` or `files.read(dir_cap, "input/a.csv")`.
   The `files` system paglet checks the capability's scope and performs the
   operation. Large reads and writes stream through artifacts.
2. **Capability handles**: a grant yields a `dir` or `file` handle with rights
   (read, write, create, delete). The paglet can derive narrower handles and
   pass them to helpers, for example a read-only handle for one subdirectory
   given to a child paglet.
3. **Mount** (for heavy I/O): a `dir` handle can be mounted as a WASI
   preopened directory inside the paglet, so normal C/C++ file APIs work
   directly within that subtree. Mounts are read-only unless the handle allows
   writing, and are removed before any snapshot or move.

### 6.5 Confused-deputy protection

Services act on the capabilities the caller passes in, not on their own broad
authority. `files.read` takes a `dir` handle as an argument; a paglet cannot
make the `files` service read something it holds no handle for.

### 6.6 Service offers: announcing host features

Hosts differ in what they can do: one has a GPU, one runs Ollama, one is a
macOS 27 (Golden Gate) machine with on-device Apple models. System paglets announce such
features as **service offers**:

- An offer names the service and operations and carries typed attributes, for
  example for `ai`: backend, models, supported tasks, context length, vision
  support, measured speed, current queue length.
- Offers are dynamic: a system paglet withdraws or updates its offer when its
  backend stops, starts or changes (for example Ollama is shut down or a model
  is pulled).
- `mesh-info` gossips offers with the host snapshots, so every host knows the
  current offers of the whole mesh. There is no central registry.
- Paglets query offers with requirements and preferences, for example
  `mesh-info.find_offers("ai", task="summarize", min_context=32000,
  prefer="shortest_queue")`.
- Transfer tickets accept an **offer target** instead of a host name: "move me
  to the best host offering `ai.summarize` that my grants and data residency
  allow". The source host resolves the target at departure time, together with
  the manifest preflight.

### 6.7 The `ai` system paglet

A native system paglet that offers local AI inference through pluggable
backends:

| Backend | Platforms | Notes |
|---|---|---|
| Apple Foundation Models | macOS 27 (Golden Gate) on Apple silicon with Apple Intelligence enabled | On-device model; the framework is Swift-only, so the host links a small Swift bridge with a C interface |
| Ollama | macOS, Linux, Windows where Ollama is installed | The host (not the paglet) talks to Ollama's local HTTP API; admins choose which models are exposed |
| llama.cpp (optional, later) | All platforms | Embedded C++ inference for hosts without Ollama; MIT license |

Operations (typed contracts, inputs as text or artifacts):

- `capabilities`: backends, models, tasks, limits.
- `summarize`, `classify` (into given labels), `extract` (fields into a
  schema), `generate` (free prompt), `embed` (vectors for semantic search),
  `describe_image` (models with vision support).
- Long requests reply asynchronously; optional progress messages.

Rules:

- Processing stays on the host: release 1 has no cloud backends, so content
  given to `ai` never leaves the host for inference.
- Grants control which owners and paglets may use which operations and
  models, with quotas (requests and tokens per time window).
- Paglets reach the AI by moving to an AI host (or by passing work to a
  paglet there); the `ai` endpoint, like every service endpoint, is re-created
  from the grant on the host where the paglet currently is.

### 6.8 The `web` system paglet

In many networks only some hosts may reach the internet, or only some hosts
are on a firewall allowlist for specific download sites. The `web` system
paglet turns such hosts into mediated web gateways: paglets move there, use
`web`, and carry the results back into the intranet.

Operations:

- `capabilities`: reachable destinations (URL patterns), search availability,
  size and rate limits, measured bandwidth.
- `search`: web search through a backend configured on that host (for example
  a self-hosted SearXNG instance or a commercial search API).
- `fetch`: HTTP(S) GET or HEAD of a page, returning status, headers and body
  (bounded size).
- `extract_text`: readable text and links of an HTML page, for further
  processing, for example by `ai`.
- `download`: stream a file into an artifact, with size limit, optional
  expected checksum, and resume for large files.

Rules:

- **Destinations are governed by the mesh**: grants carry URL scopes (schemes,
  domains, path patterns). The offer of a host lists what it can reach; a
  grant decides what a paglet may reach.
- **No access to internal addresses by default**: `web` refuses loopback,
  link-local and private address ranges, and re-checks every redirect and DNS
  result, so a web gateway host cannot be abused to reach intranet services
  (server-side request forgery). Internal destinations need an explicit admin
  rule.
- **Local secrets stay local**: credentials for search APIs or proxies are part
  of that host's local configuration; they are never put into the ledger or
  given to paglets.
- **Downloaded content is data**: it lands in artifacts with checksums and is
  never executed by the host; size, rate and volume quotas apply per owner.
- The host's own proxy settings (for example a corporate HTTP proxy) are used
  for outbound traffic.

## 7. Policy and grants

### 7.1 Mesh policy

Policy rules are ledger records. A rule matches on:

- owner key or owner group,
- module hash or module signer,
- trust class,
- host selector (all hosts, host labels, or named hosts),

and decides:

- `allow` with scope (services, operations, named roots and paths), maximum
  duration and quotas,
- `ask`: create a pending request that any mesh admin can approve or deny from
  any host,
- `deny`.

The most specific matching rule wins; the default is `deny`. Every host
evaluates the rules locally from its ledger copy.

### 7.2 Capability manifest

A paglet's passport declares the access it expects to need, for example
`files: read shared-data:/projects/**` and `server-info: load, volumes`. Uses:

- Transfer preflight: before a paglet is sent, the source host evaluates the
  manifest against the mesh policy for the target host. Movement can require
  the manifest to be satisfied, so paglets do not travel to hosts where they
  cannot work.
- Early approval: an owner can submit the manifest as a request before
  launching, so admins approve once for the whole mission.

### 7.3 Runtime requests

A paglet calls `grants.request(service, operations, scope, host selector,
duration)`. The host evaluates the policy:

- `allow`: the grant is derived from the rule; the host materializes the
  capability immediately.
- `ask`: a request record goes into the ledger; the reply is `pending`. When an
  admin decides (from any host), the decision record reaches the paglet's
  current host, which materializes the capability and sends the result as a
  message.
- `deny`: the reply is a denial with the rule ID.

Grants are mesh-wide leases: they are bound to the paglet (and optionally its
children), cover the hosts named by the host selector, expire, can be renewed,
and are revoked through the ledger.

### 7.4 Data residency

Some data must not leave certain hosts, or may only go to certain hosts (for
example "project documents may only be processed on hosts labelled
`trusted-ai`"). Because paglets carry what they read in their memory, residency
is enforced on the paglet as a whole:

- Named roots can carry a residency rule in the ledger: `host-only`, or a host
  selector such as `label:trusted-ai`.
- When a paglet reads content from such a root (through `files` or a mount),
  its host marks the paglet with that residency rule. The mark is part of the
  paglet's metadata and travels with it; it is never removed, because the host
  cannot know what the paglet kept in memory.
- Dispatch and clone are only allowed to hosts that satisfy all residency
  marks of the paglet; preflight and offer targets take them into account.
  Artifacts written by a marked paglet carry the same marks.
- Results derived from sensitive content (for example AI summaries) are
  therefore restricted too, unless an admin rule explicitly allows a
  `declassify` step for a specific paglet module.

### 7.5 Default grants

Every roaming paglet receives, on every host:

- an endpoint to `directory` (lookups filtered by visibility rules),
- endpoints to `grants` and `locator`,
- its own `storage` space and its own scratch `dir`, within quotas,
- `user-info` notify to its own owner,
- reply capabilities for requests it sends.

## 8. Enforcement layers

1. **Wasm sandbox**: separate linear memory per paglet.
2. **Worker processes**: paglets run in pooled worker processes, separate from
   the host control process, with OS-level limits and sandboxing where the
   platform supports it (see the plan, section 3.4).
3. **Import validation**: at load time the host rejects a module that imports
   anything outside the import set of its trust class.
4. **Capability checks** on every message, grant and privileged operation,
   against the local ledger state.
5. **Data residency marks** checked on every dispatch, clone and artifact
   transfer.
6. **Quotas** per paglet and per owner: memory, CPU time per handler and in
   total, mailbox size, message rate, storage bytes, number of capabilities,
   pins, and number of children and clones (to stop clone bombs).
7. **Mesh authentication and encryption**: challenge-response signatures with
   enrolled keys, end-to-end encrypted channels between hosts and for CLI
   sessions, signed ledger records, passport verification on arrival. No
   shared secrets anywhere.
8. **Audit**: grants, revocations, privileged operations and denials are
   recorded by hosts and can be queried mesh-wide by admins.

## 9. Standard import set (roaming and resident paglets)

Only these host functions are available:

- messaging: send, request, reply,
- capabilities: derive, drop, inspect,
- lifecycle of itself: clone, dispatch, deactivate, dispose; create child,
- timers and clock, secure random, logging,
- a minimal WASI subset: clocks, random, stdout/stderr (mapped to logging),
  and filesystem calls that only work inside mounted `dir` handles.

Everything else (files, system information, discovery, location, storage) is
reached by messaging a system paglet.

## 10. Threat notes

| Threat | Handling |
|---|---|
| Malicious roaming paglet | Confined by sandbox, worker process, import validation, capabilities and quotas |
| Paglet floods others with messages | Per-sender and per-receiver quotas; endpoints can be revoked |
| Capability leaks to a third party | `transferable` flag, attenuation, expiry, revocation |
| Service misused as a confused deputy | Services act only on capabilities passed by the caller |
| Paglet pinned forever to block it | Pins need the `pin` right, have a policy maximum, and admins can force-release |
| Stolen admin key | Admin set change by quorum removes it; its later records are ignored |
| Rogue host joining | Hosts must be enrolled by an admin; unenrolled keys cannot open channels |
| Compromised enrolled host | Can read and modify paglets it runs; cannot forge admin records. Admins revoke its enrollment; owners can restrict paglets to host labels |
| Sensitive file content carried to the wrong host | Data residency marks on paglets and artifacts (7.4) |
| Web gateway used to reach intranet services (SSRF) | Private, loopback and link-local destinations refused by default; redirects and DNS results re-checked |
| Paglet exfiltrates data to the internet through a web host | Grants with URL scopes (GET-only fetch and download in release 1, no uploads); residency marks keep restricted content away from web hosts |
| AI service overuse | Grants per operation and model, token and request quotas |
| Replay of old records or tokens | Signed records with logical clocks; expiry and revocation |
| Eavesdropping or tampering on the network, reverse proxies, relaying peers | End-to-end encrypted, mutually authenticated channels on top of HTTPS |
| Password or API key interception | Not applicable: only public keys and signatures are transmitted |
| Stolen admin laptop | Admin key encrypted at rest with a local passphrase (Argon2id); other admins remove the key by quorum |

## 11. Decisions

Decided by the owner:

- Security is governed per mesh by mesh admins identified by admin keys; admins
  act from any live host; no central security host.
- All hosts are equal: no central, hub or home host for security, location,
  relaying, discovery or scheduling.
- Grants are mesh-wide and follow paglets across hosts of the mesh.
- Owner keys are generated by the CLI (`paglets keys init`).
- Public-key cryptography only: no shared passwords or API keys; private keys
  never leave their machine; all channels are authenticated by signatures and
  encrypted end to end.
- The mesh locates paglets dynamically; `locate_and_pin` pins a paglet for a
  requested duration.
- No command execution service; host services are portable system paglets.

Still open:

1. Default quorum for admin set changes (1, or 2 when three or more admins).
2. How long tombstones for moved paglets are kept (proposal: 10 minutes).
3. Whether a paglet's grants may optionally extend to its children and clones
   by default, or only when the grant says so (proposal: only when stated).
