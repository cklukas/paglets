This section reports what was measured: memory images, messages and
transfers between real machines, compute work on those machines, how many
\paglet{}s one host holds, the Mesh Chronicle under failures, and the
test suite behind the earlier sections. Every number comes from a
recorded result in the repository (\path{docs/results/*.json}, written
by the tests and the live scripts themselves) or from the milestone
reports under \code{planning/}, with one stated exception; the figures
are drawn from those files by \code{figures/data.sh}. Where a number is
from a single run, this is said; where something was not measured, this
is said too.

\subsection{Setup}\label{sec:evaluation-setup}

Two kinds of results appear. The \emph{test results} come from the test
suite on the development machine, a Mac Studio (\code{Mac13,1}, macOS,
arm64, 10 CPUs), in Release builds on 2026-10-12 (the protocol checks of
2026-10-13 ran on the same machine; the checker does not record its build
type). Each test runs twice: with \paglet{}s inside the test process
(\emph{in-process}) and with \paglet{}s in sandboxed worker processes
(\emph{worker processes}, Section~\ref{sec:model}); meshes of several
hosts live in one test process and are connected by an in-memory
transport. The \emph{live results} come from a mesh of three real
machines on the author's LAN, listed in Table~\ref{tab:eval-hosts}: the
same Mac (\emph{mac}), a Raspberry Pi~4 Model~B (\emph{pi}, Linux arm64,
4 CPUs) and a uConsole built on a Raspberry Pi Compute Module~5
(\emph{uconsole}, Linux arm64, 4 CPUs). All three run \code{paglets-host
serve} built from the same sources (the Mac in a Release build; the
script records only the Mac's build type), with \paglet{}s in worker
processes and HTTPS channels between the hosts. Plain TCP between the
machines, measured with \code{iperf3} by the same script, is
934--941\,Mbit/s between mac and pi and 317--341\,Mbit/s on every pair
that includes uconsole, which is on a slower link. The script
\path{cpp/tools/mesh_bench.sh} makes a fresh mesh of the three, measures
the network, runs the File Courier, the Latency Map, the Mesh Benchmark
and Pi, and writes \path{docs/results/live_*.json};
\path{cpp/tools/chronicle_live.sh} does the same for the Mesh Chronicle.
Appendix~\ref{app:reproduce} says how to run them. Each live number is
from 2026-10-12 (the chronicle: 2026-10-13); the script runs each
transfer, each benchmark and the pi job once (the Latency Map reports the
mean and the fastest of 20 pings; \code{iperf3} runs for 5\,s), so no
variance is reported.

\subsection{Memory images}\label{sec:evaluation-images}

A \paglet{} moves as its memory image (Section~\ref{sec:movement}): the
non-zero 64\,KB pages of its linear memory, each with a SHA-256 hash, and
its exported mutable globals. The Counter example (Appendix~\ref{app:examples})
is the smallest useful case. Its test captures the image after ten
increments, serializes it, reads it back and restores it into a new
instance; the restored \paglet{} answers with the sum 55 and both copies
go on independently. The serialized image is 131\,212 bytes
(\path{docs/results/counter.json}): two 64\,KB pages of content and 140 bytes
for the header, the page table and the one global (the stack pointer),
and nothing of the module, which travels separately by hash. The module
itself, \code{counter.wasm}, is 110\,KB (112\,820 bytes) in the macOS
build of 2026-10-14; the other example modules of that build, with the
SDK and the C++ standard library linked in, are between 96\,KB (Hello)
and 828\,KB (Mesh Chronicle). These sizes are read from the build
directory and are the one exception above: they are not recorded with the
results.

Images are independent of the host's CPU and operating system. In M0, one
build of \code{counter.wasm} (the ABI~v0 version, 67\,KB) was run,
captured and resumed in four transfers between macOS arm64, Linux arm64
(the Pi~4) and macOS x86-64 (Rosetta~2), with images of 128--640\,KB; in
every transfer the count was intact and the \paglet{} continued counting
(\code{cpp-m0-results.md}, section ``Cross-architecture memory
images''). The same report gives the cost of the primitives with WAMR
2.4.5 in a RelWithDebInfo build: capturing a two-page image takes 1.0\,ms
on the Mac and restoring it 0.05\,ms; on the Pi~4, 6.5\,ms and 0.9\,ms,
measured while a compiler build was using all four cores. The capture is
dominated by the SHA-256 of every page, a portable C++ implementation.
Instantiating a module, running its initializer and destroying the
instance takes 36\,$\mu$s on the Mac; a call from the host into the guest
0.4\,$\mu$s.

The benchmark cases of the test suite (\code{bench:}, at full size with
\code{PAGLETS\_BENCH=1}) measure the runtime's operations around the
engine: request and reply, activation, memory per \paglet{} and moves. On
Linux x86-64 with 4 CPUs (\code{cpp-benchmarks.md}): a request and reply
to an active \paglet{} 15\,500 times per second with a median of 0.06\,ms
in-process (15\,200 per second, 0.05\,ms with worker processes); the
activation of an inactive \paglet{}, that is loading its image, placing
the instance and delivering the message, a median of 0.64\,ms in-process
and 5.9\,ms with workers, where the image has to reach the worker; a move
between two hosts of one process over the in-memory transport, with
4\,MB of unchanging memory in the \paglet{}, a median of 31\,ms
in-process and 93\,ms with workers. The move test also records page
reuse: 66 pages travel on the first move and 2.2 on average on later
ones, because the receiving host keeps the pages it has seen by hash and
skips them (Section~\ref{sec:movement-protocol}). The 4\,MB ballast is
sent once.

\subsection{Messages and transfers between real hosts}\label{sec:evaluation-mesh}

Two example \paglet{}s measure the live mesh from the inside. The Latency
Map places a probe on every host; each probe sends a \code{ping} request
to each other probe 20 times, one at a time, and records the mean and the
fastest round trip (Section~\ref{sec:communication},
Table~\ref{tab:comm-latency}). Figure~\ref{fig:eval-latency} shows the
six ordered pairs. A round trip passes both runtimes, the worker process
boundary on both sides and the encrypted channel between the hosts. The
means are 1.16--5.16\,ms and the fastest round trips 0.79--1.92\,ms. The
two Pi-class hosts talk fastest with each other (1.16 and 1.34\,ms mean),
on the pair whose TCP throughput is the lower one; every pair with the
Mac is slower (2.84--5.16\,ms), so the Mac side adds about 2\,ms to a
round trip. The recorded data do not say why, and the measurement was not
repeated. (The same example inside one test process reports 7--10\,ms,
\path{docs/results/latency.json}; that measures the test fixture, which
delivers frames in rounds with a 2\,ms pause, not the runtimes.)

The File Courier, an example \paglet{} that uses the \code{share} and
\code{save} operations of the \code{files} service and the artifact
capabilities of Section~\ref{sec:mesh}, carries files between named roots
of two hosts. It does not copy the content into its memory: it shares the
files on the source host as artifacts and saves them on the destination,
whose host fetches every part directly from the source over the channel
between the hosts, checks the SHA-256 and writes the file.
\code{mesh\_bench.sh} lets a courier carry payloads of 16, 64 and 256\,MB
of random bytes for every ordered pair of hosts and records two times
that the courier measures itself: \emph{sharing} on the source (reading
and hashing the files) and \emph{saving} on the destination (fetching,
checking, writing). The transfer rate is the payload divided by the saving
time. Figures~\ref{fig:eval-transfer-time} and \ref{fig:eval-transfer-rate}
show the 18 transfers. Saving 16\,MB takes 0.48--0.78\,s, 64\,MB
1.6--2.9\,s and 256\,MB 9.4--12.3\,s; the rates are 20.4--39.6\,MB/s, most
of them between 20 and 28\,MB/s, and they do not grow with the payload.
Against the TCP baseline this is 18--35\,\% of the link between mac and
pi (941\,Mbit/s, about 112\,MB/s) and 54--68\,\% of the links with
uconsole (317--341\,Mbit/s, 38--41\,MB/s). On the gigabit link the
exchange is bound by the hosts, not by the network; the recorded data do
not split the saving time into its parts (the HTTPS channel, the parts of
1\,MB, the hash check and the file writes), so where the time goes is a
question for profiling. Sharing shows the cost of reading and hashing
alone: 17--23\,ms for 16\,MB and 194--388\,ms for 256\,MB on mac and
uconsole, but 120--181\,ms and 1.8\,s on the Pi~4, about 140\,MB/s.

What these numbers do not give is the time of a \paglet{}'s move between
two real machines. The move protocol runs over the same channel as the
content exchange, and an image is at most 16\,MB of pages, so the
transfer part of a move is within what the courier numbers show; what a
move costs on top (capturing and hashing the image, its way through the
worker processes on both sides, the protocol's round trips,
Figure~\ref{fig:movement-protocol}, and, when the destination does not
hold the module, the module itself) is not measured between real
machines. \code{mesh\_bench.sh} does not time a move; the only timed moves
are those of the benchmark test on the in-memory transport above. Moves
over HTTPS are exercised, not timed: by the \code{host\_serve\_move} test
between two host processes on the loopback interface of one machine, and
between real machines by the Pi job's clones and by the Mesh Chronicle.
Timing them is listed as open in \code{cpp-benchmarks.md}.

\subsection{Compute on the mesh}\label{sec:evaluation-compute}

The Mesh Benchmark sends a clone of itself to every host. Each clone takes
a compute slot (Section~\ref{sec:mesh}), runs integer, floating-point and
memory-copying loops in its own WebAssembly code for one second each, and
writes and reads 8\,MB through its storage service in blocks of 256\,KB.
Table~\ref{tab:eval-benchmark} is the live run. The CPU numbers are of
the WAMR fast interpreter running the \paglet{}, not of native code: 250
million integer operations per second on the Mac, 180 on the uconsole and
67 on the Pi~4; the floating-point loop is faster on the uconsole (331
Mflops) than on the Mac (266). Memory copying in the \paglet{}'s linear
memory reaches 27\,000\,MB/s on the Mac. The storage path is the slowest part
on the Mac: 45\,MB/s for writing, with every 256\,KB block one request
from the worker process to the host that writes it, against 397\,MB/s on
the uconsole; this difference is not explained by the recorded data and
is a candidate for profiling.

Pi puts the slots to work. The job cuts the hexadecimal digits of $\pi$
into chunks, asks \code{mesh-info} for hosts with free slots, clones
itself with one chunk onto each, takes the answers in order into a file
on its host, sends a chunk out again when it is not answered in time, and
converts the result into decimal digits at the end
(Section~\ref{sec:mesh}, \path{docs/examples/pi.md}). On the live mesh it
computed 100\,000 hexadecimal digits in 200 chunks of 500, with at most 32
in flight, on all three hosts with one slot per CPU: the hexadecimal
digits took 313\,s, the conversion into 120\,409 decimal digits less than
a second at the one-second resolution of the script's polling, and the
first 100 decimal digits were checked against the known value
(\path{docs/results/live_pi.json}, 2026-10-12). The test of the example
is smaller and harder: three hosts in one process with two slots each,
1\,200 digits in 40 chunks, and the third host is shut down while one of
its workers runs. The job finishes with all 40 chunks, and the chunks it
sent again after the loss are counted: 6 in-process and 3 with worker
processes in the recorded runs (\path{docs/results/pi.json}; 6.1\,s and
4.2\,s).

\subsection{Many paglets on one host}\label{sec:evaluation-density}

How many \paglet{}s a host holds was measured first in M0 with
\code{paglets-spike} on the Counter module and the WAMR runtime alone. On
the Mac, 1\,000 live instances in one process were tested, with 137\,KB
of resident memory per instance. On the Pi~4 the first run stopped at 59
instances: WAMR's hardware bound checks reserve 8\,GB of virtual address
space per instance, and the Pi's kernel has a 39-bit address space; with
software bound checks the Pi also held 1\,000 instances at 89\,KB each
(\code{cpp-m0-results.md}, finding 2). The Linux CI jobs repeat this
measurement with 1\,000 instances of the Counter on every push to the
\code{cpp} branch (\path{.github/workflows/cpp.yml}); the output is
printed, not recorded. With the runtime, M1 measured 23\,000--56\,500
host requests per second spread over 200 \paglet{}s on Linux x86-64 with
4 vCPUs, depending on lanes and mode (\code{cpp-m1-results.md}, section
``Measurements''). The benchmark tests put the host's resident memory
per \paglet{} at 134\,KB in-process and 46\,KB with worker processes,
where the instances live in the workers (\code{cpp-benchmarks.md}).

\subsection{Fault tolerance in practice}\label{sec:evaluation-chronicle}

The Mesh Chronicle (Section~\ref{sec:zombies}, Appendix~\ref{app:examples})
is a zombie \paglet{} that keeps a life log of its mesh and delivers it as
Markdown when its lifetime is over. \code{chronicle\_live.sh -{}-late uconsole}
ran it for ten minutes on the live mesh on 2026-10-13 with failures on a
schedule: at 60\,s the uconsole joined the mesh and got a replica; at
92\,s the host of the main (pi) was frozen with \code{SIGSTOP}, cut off
with its state intact, and thawed at 180\,s, so that two mains met; at
271\,s pi was killed and at 360\,s restarted from its state; at 420\,s
the uconsole was killed for 90\,s; at 525\,s the sink's host, the Mac,
shut down normally and came back at 555\,s. The life log it delivered is
reproduced in \path{docs/examples/mesh-chronicle-log.md};
\path{docs/results/live_chronicle.json} records the outcome the script
checked (three replicas, two takeovers, one partition with a main on both
sides, 20 protocol steps conformant, no replica left), and the script
fetched the log from the sink, the Mac, once. The log shows two
takeovers: the Mac took over as main at 17:16:33 after 38\,s without a
sample from the frozen pi, and pi took over again at 17:23:44 while the
Mac was down; one partition with a main on both sides for 1\,min 15\,s
(the frozen pi's main and the Mac's), whose journals were merged into one
log when the sides met; 55 samples of the mesh at 10\,s intervals; 53\,s
in all without a working main, the longest gap 38\,s; and the log
delivered to the sink. The 20 protocol steps that the three hosts
recorded were replayed through the specification of
Section~\ref{sec:zombies} and conform to it.

The run is one run, and the schedule is the one the script has; it is
evidence that the protocol behaves on real machines as the model says,
not a measurement of availability. What the model checker establishes,
and its numbers, are in Section~\ref{sec:zombies}
(Table~\ref{tab:zombie-results}): ten two-replica worlds explored
completely, two three-replica worlds to depth 11, and 10\,000 timed
random runs without a failure. The twelve explored worlds took 39 minutes
on the Mac and the random runs 28\,s (\path{docs/results/zombie_protocol.json},
2026-10-13); the random runs sum to 213\,901\,s of simulated time with
two working mains, which is the price of the partition tolerance the live
run shows. The limits of these checks (hash compaction in every world,
with an omission probability of about $n^2/2^{129}$ for $n$ states; the
depth bound for three replicas; and what the model leaves out) are
stated in Section~\ref{sec:zombies}.

\subsection{The test suite as evidence}\label{sec:evaluation-tests}

The claims of Sections~\ref{sec:model} to \ref{sec:tools} rest on the
test suite more than on the numbers above. At the time of writing,
\code{cpp/tests/} registers 252 test cases with \code{PAGLETS\_TEST},
from the codecs and the engine through the runtime (47 cases), the mesh
(19), movement, location, policy, services, the network and the gateways
to the example \paglet{}s (12) and the zombie protocol (9). \code{ctest}
runs them twice: as \code{unit} in-process and as \code{unit\_workers}
with \code{PAGLETS\_TEST\_WORKER} set, so that every case also runs with
sandboxed worker processes. Thirteen more \code{ctest} cases drive the
binaries from outside, among them the worker's sandbox check, image save and resume
across two processes, the host's state directory across two processes,
\code{host\_serve\_move} (a Counter moved between two hosts over HTTPS on
loopback and back), \code{host\_mesh\_discovery}, the ledger CLI, an
out-of-tree package build, and \code{docs\_sync}, which fails while a
documentation page or this paper is not current with the sources. The
multi-host tests run several hosts in one process, connected by the
in-memory transport or by HTTPS on loopback; they cover the mesh, moves,
location, relays, the content exchange, the examples and the gateways.
Eight \code{fuzz:} cases mutate valid inputs for every decoder of data
from outside, from MessagePack values and ledger records to modules,
images and the frames between hosts. CI runs the suite on Linux x86-64
and arm64 with GCC~16, on macOS arm64, under AddressSanitizer with
UndefinedBehaviorSanitizer and under ThreadSanitizer, and on Windows
x86-64 with MinGW-w64 as an experimental job whose failure does not fail
the workflow (\path{.github/workflows/cpp.yml}).

The result tables of the documentation come from the example tests: most
run their example on a mesh of several hosts in one process, the smallest
(Hello, Ping Pong, the Counter's image test) on one runtime; all run in
both modes, check what the example must show, and with
\code{PAGLETS\_RESULTS\_DIR} set write what they measured to
\path{docs/results/<example>.json} (Appendix~\ref{app:reproduce}).

\subsection{What is not measured}\label{sec:evaluation-gaps}

No move between real machines is timed, only moves over the in-memory
transport. The live numbers are single runs on three machines of one LAN,
without variance, and no mesh is larger than five hosts in the tests or
three real ones. Only WAMR's fast interpreter was measured, not its AOT
or JIT modes (Section~\ref{sec:discussion}). The density numbers are of a
\code{paglets-spike} process and of a cloud container, not of a real
mesh, and no run holds thousands of \paglet{}s for hours. The Windows
build is an experimental CI job whose failure does not fail the workflow;
at the time of writing it does not pass, and it has no recorded numbers.
Relays and the gateways (Section~\ref{sec:mesh}) are tested, not
measured.
