\subsection{Portable state and module checks}\label{sec:model-instance}

A paglet module is a single-threaded \code{wasm32-wasip1} reactor: the
host calls its exported functions repeatedly, rather than starting a new
program for every message. The module runs as a \emph{guest} inside the
host runtime. Each instance owns one linear memory and its mutable
globals, which are global variables whose values can change. The software
development kit (SDK) stores the paglet object, heap, handlers and
callbacks for pending operations in linear memory. These callbacks are
also called \emph{continuations}.

After a handler returns, the Wasm engine's operand and control stacks are
empty. The C/C++ stack used to store values in memory (the \emph{shadow
stack}) lies in linear memory; its stack pointer is an exported mutable
global. Capturing memory and these globals produces an \emph{image} of the
supported instance state, without interpreting C++ object layouts.

Before accepting a module, the host checks that all required state can
be captured. It requires one exported memory and access to every mutable
global defined by the module. It rejects unsupported reference or vector
globals, host-supplied state, and instructions that modify function
tables. The module itself fixes those tables. Imports are restricted to
the paglet application binary interface (ABI), which defines calls between
the host and guest, and a subset of WASI. A guest therefore cannot obtain
unrecorded operating-system resources through unrestricted system calls.
Each saved image records its module's SHA-256 hash and can be restored
only with that module version. The checks are implemented in
\sourcefile{cpp/host/src/wasm_binary.cpp}{\code{wasm\_binary.cpp}} and
\sourcefile{cpp/host/src/wasm_snapshot.cpp}{\code{wasm\_snapshot.cpp}}.

\subsection{Execution and host-managed permissions}\label{sec:model-capabilities}

Figure~\ref{fig:model-architecture} separates guest state from host state.
Each scheduler thread controls one worker process; an active instance
stays with that thread. Workers run in platform sandboxes that restrict
their access to the host. If a required worker fails its startup check,
host startup fails. Explicit execution inside the host process is also
available for embedding and tests. WAMR interprets mobile instances, with
configurable limits on memory growth and elapsed time per handler.

A guest accesses other paglets and host resources through positive integer
\emph{handles}. Each handle refers to a \emph{capability}: a host-managed
record specifying a resource, the permitted operations and any expiry or
use limit. It can also record which grant it derives from. The integer
can appear in guest memory, but the host decides whether it still grants
access. Copying guest memory alone therefore does not copy permission
to use a resource on another host.

Messages use the MessagePack binary format~\cite{msgpackSpec}. Host-side
code uses C++ reflection to derive encoders and decoders; generated guest
code follows the same message schema~\cite{p2996r13}. A message schema
defines the data fields and their types. Encoding a message is separate
from capturing the whole agent's state.

Native system services control access to files, large stored objects
and policy. File access requires a directory capability lent to the
paglet. Resolved paths must remain inside that directory. Large content
travels as \emph{artifacts}, stored objects identified by a content hash,
rather than as part of the paglet's heap. Section~\ref{sec:movement-record}
explains how the destination reconstructs the capability table.

Memory and execution-time requirements default to unknown. Hosts impose
no memory or execution-time policy ceiling unless their operators enable
one. The current Wasm32 implementation still has a technical address-space
boundary of 4\,GB per instance; physical memory can run out earlier.
An operator can require declarations and refuse a module or job whose
declared memory allowance does not fit. These allowances bound linear-memory
growth; they do not reserve physical RAM or meter total process memory,
host-side buffers or worker overhead. The module specifies its initial
memory. Message documents retain a separate 1\,MB size limit.

Guest code can handle a failed \code{memory.grow} or an allocation that
returns a null pointer. Ordinary C++ \code{new}, however, aborts on failure
in these guests, which do not use exceptions; that failure ends the
paglet. An access outside linear memory traps. An enabled handler watchdog
or job-time budget interrupts work exceeding its elapsed-time allowance.
