\subsection{Identity, policy and host restrictions}\label{sec:mesh-policy}

A \emph{mesh} is a group of cooperating hosts. Its trust configuration is
a signed ledger of administrators, hosts, owners, trusted modules and
resource policies. New records are appended rather than replacing old
ones. Hosts exchange records and apply them in a deterministic order.
Removal and revocation rules prevent later signatures by a removed
authority from restoring its access. Each host enforces the ledger
records it has received; a disconnected host cannot enforce a revocation
it has not yet learned.

A passport binds the paglet's identity to its owner and module.
An owner-launched identity is derived from the owner's key and a new
owner-local value used once (a \emph{nonce}). Children and clones extend
a signed chain of identities. The destination verifies that chain rather
than accepting an arbitrary identifier from the caller. The host adds
verified sender information to delivered messages and checks resource
requests against ledger policy.

A copied or derived capability keeps its link to the original grant.
Releasing or revoking that grant invalidates its copies and derivatives
once the enforcing host receives the record. Access to a resource can
also add a \emph{residency mark}, restricting where the paglet may run.
For example, reading content confined by policy to one host prevents
the marked paglet from leaving it. The restriction follows the read
because the data may now be in guest memory, even if the file handle is
later closed. It does not protect against a malicious enrolled host.

The implementation is divided between
\sourcefile{cpp/host/src/node/movement.cpp}{transfer checks},
\sourcefile{cpp/host/src/mesh/ledger.cpp}{ledger processing} and the native
\sourcefile{cpp/host/src/services/files.cpp}{file service}. A capability
permits an operation; it does not make that operation and a checkpoint
one atomic transaction.

\subsection{Mobile coordination and host-specific computation}\label{sec:mesh-compute}

A long computation inside a handler delays the coordinating agent's next
message and state capture, even without a watchdog. Compute jobs let that
agent submit a function and input instead. The host
runs a separate instance in a job pool and delivers its result later.
The coordinating paglet can handle messages while the job runs. The
job's active call stack stays on its execution host and cannot itself
be migrated.

The existing \code{patterns::Task<Request, Result>} represents the
coordinating paglet, with start, status, wait and cancel operations.
\code{tasks::TaskHandle} is a shared control interface for its child work,
returned by service helpers or by \code{compute::Job::task()}. Tracking
these handles propagates cancellation from the overall task. The two
execution backends differ in authority: native services retain filesystem
and other resource capabilities on their host, while isolated compute
jobs receive input and output operations, clocks, progress and cancellation,
without filesystem, network or paglet-messaging capabilities.

A job reserves the requested number of CPU slots. Queued jobs share
capacity with cooperative compute-slot leases, which reserve capacity
for application-managed work. Each queue serves jobs in arrival order; its first job reserves the
capacity it needs against later arrivals. Job duration is unlimited by
default. A developer can request unlimited time explicitly or declare a
positive elapsed-time budget, including a week or longer. Operators and
mesh policy can impose ceilings and require finite declarations.
Elapsed-time budgets do not meter cumulative CPU time. Expiring a
cooperative lease does not interrupt arbitrary CPU work. Imported
functions let a job report progress and check cancellation; the runtime
interrupts cancelled or over-budget jobs. Job memory allowances are
independent of the coordinator's allowance.

Mesh File Finder illustrates the service backend. The
\sourcefile{cpp/sdk/include/paglets/patterns/files.hpp}{\code{scan\_files} helper}
starts native background scanning and delivers bounded batches with
progress, rather than holding a handler or collecting the whole tree.
Each batch checks directory authority; cancellation releases the cursor.
An already blocked OS call must return before native cancellation can
finish. Cursors remain on the filesystem host and are not restored from
the agent's checkpoint. Recovery requires a new scan; background execution
alone does not make an operation durable.

When \code{paglets-wamrc} is available, the host compiles job modules for
its own CPU and caches the result; otherwise it interprets them. Paglets
themselves remain interpreted, and Windows jobs currently use the
interpreter. Compilation, queueing and execution have separate costs.
Section~\ref{sec:evaluation-compute} compares only execution with compiled
code already cached, called \emph{warm AOT} execution.

Inputs can refer to artifacts, and outputs exceeding the message size
limit are returned as artifacts. Normally a job ends when its coordinator
ends or leaves the host. An explicit option lets it finish and send its
result after the coordinator moves. Control of job status and cancellation
stays with the original host. If the executing host is lost, the mesh
reports the job as \code{gone}; the coordinator decides whether to retry.
After a restart, pending jobs are also reported as gone, because their
active stacks are not recovered. Jobs therefore offer less recovery
support than the replicated agents in Section~\ref{sec:zombies}, without
requiring replication for independent compute tasks. Full implementations
are in \sourcefile{cpp/host/src/runtime_jobs.cpp}{\code{runtime\_jobs.cpp}}
and \sourcefile{cpp/examples/pi/pi.cpp}{the Pi coordinator and jobs}.
