\subsection{Ordering checkpoints and merging observations}\label{sec:zombies-design}

A \emph{zombie paglet} has copies, called \emph{replicas}, on several
hosts. Its group can continue after a member host fails. One replica normally acts
as \emph{main} and advances the work; the others keep checkpoints.
A network partition can leave several mains running at once. The protocol
therefore separates work state from observations; it does not impose
one global order on every action during a partition.

\emph{Work} follows a chain of checkpoints. A rank compares checkpoints
by completion status, progress, leadership counter (called \emph{reign}),
checkpoint number and author ID, in that order. The first differing
field decides: completed work and larger progress or counter values
rank higher; a lower author ID breaks the final tie. A new main chooses a reign above
all it has seen, saves a checkpoint and announces its rank. Replicas
adopt higher-ranked checkpoints. Work on a losing chain is discarded.

\emph{Observations} are separate journal entries identified by observer,
restart number and entry number. Journals merge by taking the union of
their entries. Version vectors summarize the entries held for each
observer and restart, allowing missing entries to be
requested~\cite{parker1983versionVectors}. Concurrent observations can
therefore survive a merge even when only one chain of work continues.

Applications must respect this distinction. Work progress must not
decrease along a checkpoint chain. Effects other than the final result
should be safe to repeat (\emph{idempotent}) or protected separately by
the application. The protocol does not make all operations appear to
occur in a single order consistent with real time (\emph{linearizability}).
An observation saved only on a crashed host may be absent from a result
delivered before that host returns. Saving an observation durably does
not guarantee that other replicas have already received it.

\subsection{Saving state before externally visible actions}\label{sec:zombies-durability}

The protocol is implemented by
\code{step(State\&, Input) -> Outputs}. Given a state and input, this
function changes the state and returns an ordered list of requested
actions: send a message, save state, change a timer, do work or deliver
a result. It makes no network or ABI calls itself. This separation lets
the runtime and checker execute the same protocol code.
Listing~\ref{lst:zombie-persist-order} shows a new main saving its
checkpoint before announcing it. A reign resembles a leadership number
in Raft~\cite{ongaro2014raft}; the partition behavior and journal merging,
however, do not implement Raft consensus.

% snippet: cpp/common/include/paglets/protocols/zombie/zombie_impl.hpp#paper_persist_order [caption={Saving a new main's checkpoint before announcing it},label={lst:zombie-persist-order}]
\begin{lstlisting}[style=paglets-cpp,caption={Saving a new main's checkpoint before announcing it \src{cpp/common/include/paglets/protocols/zombie/zombie\_impl.hpp}},label={lst:zombie-persist-order}]
become(s_.done ? Role::delivering : Role::main, cause);
persist();
broadcast(beat());
set(Timer::beat);
\end{lstlisting}
% /snippet

The code that carries out these actions must preserve their order and
finish each requested save before the next externally visible action.
The SDK cannot save an image during a handler. It instead requests a
checkpoint, stores the remaining actions in guest memory and sends
itself a message to continue on the next call
(Listing~\ref{lst:zombie-barrier}). After a restart it discards old deferred
actions and rejoins in the recovering role. If a required durable write
fails, the runtime must end the paglet as failed. Checking the transition
function alone does not verify these SDK and storage requirements.

% snippet: cpp/sdk/include/paglets/patterns/zombie.hpp#paper_persist_barrier [caption={Saving a checkpoint before carrying out remaining actions},label={lst:zombie-barrier}]
\begin{lstlisting}[style=paglets-cpp,caption={Saving a checkpoint before carrying out remaining actions \src{cpp/sdk/include/paglets/patterns/zombie.hpp}},label={lst:zombie-barrier}]
if (std::holds_alternative<zp::Persist>(o)) {
    (void)checkpoint();
    deferred_.insert(deferred_.end(), outs.begin() + static_cast<std::ptrdiff_t>(i) + 1, outs.end());
    if (!flush_pending_) {
        flush_pending_ = true;
        SendOptions options;
        options.async = true;
        (void)self().send("zombie.flush", std::move(options));
    }
    return;
}
\end{lstlisting}
% /snippet

A periodic status message, called a \emph{beat}, can include membership
information or observations not yet saved durably. These are saved at a
later checkpoint or by a replica that fetches them. This does not change
the rule that a new checkpoint is saved before being announced. It does
mean that a message can contain other information that is not yet durable
everywhere.

\subsection{Failure detection and result acceptance}\label{sec:zombies-recovery}

A replica suspects a silent main after ten seconds plus a random delay
of up to five seconds. It collects status reports and selects the best
rank, preferring an existing leader and then the lower replica ID in a
tie. A restarted replica first listens in the recovering role. When two
mains communicate, the less advanced one passes on its observations
and steps down; the other may pause work while ranks settle. The timers
balance recovery delay against false suspicions. They cannot prevent
concurrent mains during a network partition.

A \emph{sink} receives and stores results. It saves the first accepted
result for a group and sink number before acknowledging it. Repeated
delivery of that result succeeds without storing another result.
The owner can redirect delivery to another sink, increasing the sink
number; each redirect can therefore allow one more accepted result.
The checked bound is one accepted result plus at most one per redirect.
It assumes the model's sink can save and accept a result atomically.
Permanent rejection for policy, size or format ends the group as failed
and notifies the paglet. Temporary transport or storage failures can
be retried.

New hosts offering the service can join the group, with at most one
replica per group on each host. There is no safe removal of old members.
Repeated joins and departures therefore increase both retained membership
and the messages sent per beat. The implementation is linked as
\sourcefile{cpp/common/include/paglets/protocols/zombie/zombie.hpp}{protocol types},
\sourcefile{cpp/common/include/paglets/protocols/zombie/zombie_impl.hpp}{transitions}
and \sourcefile{cpp/sdk/include/paglets/patterns/zombie.hpp}{SDK actions}.

\subsection{What the model checker verifies}\label{sec:zombies-check}

The checker explores possible execution states by running the same
transition function as the library. Each model configuration, called a
\emph{world}, adds hosts, saved state, registries, ordered message channels
and limits on faults. Breadth-first search checks four safety invariants,
properties that must hold in every explored state: the result-count bound
under redirects; preservation of the best durably saved progress;
preservation of durable observations somewhere until the group ends; and reporting of every role change, with only permitted changes allowed.

The first recovery goal is a single main whose followers share its
checkpoint and journal, or a replica that has already entered the ended
state. The second is termination of all joined replicas after result
acceptance or owner cancellation. From each reachable state, there must
be some sequence of fault-free steps leading to each goal. This property,
written AG EF, proves that recovery remains possible. It does not prove
that every execution eventually recovers, even if continuously enabled
actions are eventually taken (\emph{weak fairness}).

To limit memory use, the checker records visited-state identities as
128-bit hashes instead of retaining full states for comparison. This
technique is called \emph{hash compaction}~\cite{stern1995hashCompaction}. It also renames leadership
counters while keeping their order and whether values are consecutive.
This gives equivalent states a finite representation. It uses explicit-state search like Murphi and
TLC~\cite{yu1999tlc}, but does not include a general temporal-logic engine,
fairness checking or reduction of redundant event orderings.
Hash collisions could hide a state, and incorrect counter renaming could
merge distinct behavior. The estimated omission probability is below
$10^{-24}$ for the largest recorded world if hashes behave randomly.
Correctness of the renaming is assumed, not mechanically proved.
Section~\ref{sec:evaluation-zombies} reports the worlds and search limits,
separately from simulations and physical tests.
