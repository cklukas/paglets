A \paglet{} is a WebAssembly instance that the host calls into, one call at
a time. Everything that happens to it, from its creation to its end, is a
sequence of such calls: the handlers of Section~\ref{sec:model} for
messages, and \emph{hooks} for the transitions of its lifecycle. This
chapter defines the states a \paglet{} can be in, the hooks the SDK offers
for the transitions, and exactly when each hook runs relative to the
handler that caused the transition. The ordering matters because a
\paglet{} moves as a memory image: the image is taken between two calls,
and the hooks are what runs on either side of it. Appendix~\ref{app:events}
summarizes the result as a reference.

\subsection{States and transitions}\label{sec:lifecycle-states}

Figure~\ref{fig:lifecycle-states} shows the states and the hooks on the
transitions. A \paglet{} is \emph{new} between its creation and its first
call; \emph{active} while it has an instance on a lane of its host (a
worker thread that runs one call at a time, Section~\ref{sec:model});
\emph{inactive} while it exists only as a memory image, in the host
process or in the host's state directory; \emph{moving} while its image is
in transit to another host; and \emph{ended} after disposal or a failure.
A clone starts \emph{new} like a created \paglet{}, but with a copy of the
original's memory. Within a host, the runtime distinguishes only
\code{active} and \code{inactive}; the other states are the view from the
\paglet{}'s side.

A \paglet{} requests the transitions itself, through the SDK functions
\code{deactivate}, \code{dispatch}, \code{clone\_raw} and \code{dispose};
or the host requests them on behalf of an operator: the CLI has
\code{dispatch} and \code{dispose} commands, the web UI the same; the
runtime's API can also deactivate a \paglet{}, which no tool exposes
today. Both paths run the same hooks. A message, a timer or the end of a
\code{wake\_after\_ms} delay turns an inactive \paglet{} active again; so
does the arrival of a report such as \code{on\_move\_failed}.

\subsection{Hooks run between handlers}\label{sec:lifecycle-hooks}

The rule that makes the lifecycle easy to reason about is that a hook is a
call like any other: the host calls into a \paglet{} from one thread at a
time, and takes memory images only between two calls, never while a call
is in progress. A \paglet{} therefore never sees two calls at once, and
never has a handler interrupted by a hook. A lifecycle operation requested
inside a handler does not take effect in that handler. \code{dispatch},
\code{deactivate}, \code{dispose} and \code{clone\_raw} record the request
and return at once; the handler continues and returns; only then does the
host act. The order after the handler is fixed:

\begin{enumerate}[nosep]
  \item The images of the clones requested in this handler are taken
    (one snapshot serves all of them); each local clone is started with
    \code{on\_cloned}, and each clone for another host is set aside for
    the mesh, which receives it once the lane has finished this call.
  \item The one pending end operation runs. For \code{dispose}:
    \code{on\_disposing}, then the end. For \code{dispatch}:
    \code{on\_dispatching}, then the image, then the departure. For
    \code{deactivate}: \code{on\_deactivating}, then the image, then
    the release of the instance.
  \item Otherwise, if a checkpoint is due (\code{checkpoint()} was called,
    or the checkpoint interval has passed), the image is stored.
\end{enumerate}

At most one of \code{dispose}, \code{deactivate} and \code{dispatch} can
be pending per handler call; the second request fails with
\code{bad\_state}. Clones combine with any of them, up to the host's limit
of children and clones per call (16 by default, \code{quota} beyond).
Figure~\ref{fig:lifecycle-dispatch-order} shows the sequence for a handler
that calls \code{dispatch}.

\subsection{Creation, clones and start arguments}\label{sec:lifecycle-start}

A \paglet{} comes into being with a module hash, an owner and a trust
class, and a start document: the arguments and the capabilities its
creator passes. The creator is the host (on behalf of the CLI's \code{run}
or \code{launch}, with \code{--args JSON}), or another \paglet{} through
\code{create\_child}. The host queues the \code{created} event at a
priority above every message priority, so it is the first call even if
messages were sent to the new \paglet{} before it ran. At that first call
the module's \code{\_initialize} export has run, which constructs the C++
static objects, and the SDK constructs the one \code{Paglet} instance that
\code{PAGLETS\_PAGLET} registers. Its constructor is where handlers are
registered, and it runs once in the life of a \paglet{}: a clone or a
restored image already contains the constructed object, so the
constructor does not run again for them. (\code{\_initialize} is run by
the engine whenever it instantiates a module that imports WASI, a restore
included; the image then overwrites everything it did, so a \paglet{}
never observes a second run.)

The SDK passes the start document as a \code{Started}: the raw
\code{args}, the \code{caps} as \code{Capability} handles that are already
in the \paglet{}'s table, and \code{original}, set only for clones.
\code{decode\_args} decodes the arguments into a schema type. The counter
example uses it for an optional initial value:

% snippet: cpp/examples/counter/counter.cpp#created [caption={The counter's start arguments},label={lst:lifecycle-created}]
\begin{lstlisting}[style=paglets-cpp,caption={The counter's start arguments \src{cpp/examples/counter/counter.cpp}},label={lst:lifecycle-created}]
// Optional start arguments (`--args '{"value": 10}'`).
void on_created(paglets::Started& s) override {
    Start start;
    if (!s.args.empty() && s.decode_args(start)) value_ = start.value;
}
\end{lstlisting}
% /snippet

A \paglet{} that gets no arguments sees empty \code{args}; the decoder
rejects empty input, so the test on \code{args.empty()} in
Listing~\ref{lst:lifecycle-created} is not needed; it only states the
intent. A child made with \code{create\_child} gets the capabilities in
the call and the host's service endpoints that every new \paglet{}
receives, and no endpoint to its creator unless one is passed; the creator
gets an endpoint to the child as the result.

A clone is different in two ways. Its memory is a copy of the original's
image, taken after the handler that called \code{clone\_raw}, so it begins
with the original's state as that handler left it. That includes the
reply continuations of the original's outstanding requests, which never
run in the clone, because the replies go to the original. Its first call is
\code{on\_cloned}, not \code{on\_created}, with the arguments and
capabilities of the \code{clone\_raw} call and the original's ID in
\code{original}. The clone's capability table holds its own endpoint
(handle 1), copies of the original's transferable endpoints under the same
handle numbers, so handles stored in the copied memory stay meaningful,
the service endpoints of the host, and the capabilities passed to it;
reply, timer and non-transferable capabilities are not copied. The fan-out
pattern of Section~\ref{sec:movement} builds on this: the original keeps
its role as the coordinator, each clone learns from \code{on\_cloned} that
it is a worker, decodes its share of the work from the arguments and takes
the endpoint back to the original from the capabilities. The pi example
disposes a clone at once when either is missing. Clones inherit the
original's data-residency marks and its restart policy.

\subsection{Deactivation and activation}\label{sec:lifecycle-deactivation}

\code{deactivate} ends the \paglet{}'s instance without ending the
\paglet{}. After the handler, the host calls \code{on\_deactivating},
takes the image, and stores it: on a host with a state directory it goes
to disk, otherwise it stays in the host's memory. The instance is then
released, with its lane and its compiled module. The capability table,
the mailbox, pending requests and timers are host state and stay as they
are. While it waits, the \paglet{} holds no instance and no lane; the host
keeps its record, its capability table, its mailbox and its timers, and,
without a state directory, the image itself in memory.

Three things wake it on its own account: a message (including a reply or
a report), a timer set with \code{after}, or the \code{wake\_after\_ms}
given to \code{deactivate}; a dispose or a dispatch requested through the
host's API activates it as well, since the request is a delivery. In each
case the host instantiates the module from the image and calls
\code{on\_activated} right before the delivery that woke the \paglet{}.
For \code{wake\_after\_ms} there is no delivery: \code{on\_activated} is
the only call, and the \paglet{} decides there what to do. The watcher
example, which sleeps between checks of release pages, uses it to tell a
wake-up on time from a message that came earlier
(Listing~\ref{lst:lifecycle-wake}):

% snippet: cpp/examples/watcher/watcher.cpp#wake [caption={The watcher's \code{on\_activated}: a wake on time or a message},label={lst:lifecycle-wake}]
\begin{lstlisting}[style=paglets-cpp,caption={The watcher's \code{on\_activated}: a wake on time or a message \src{cpp/examples/watcher/watcher.cpp}},label={lst:lifecycle-wake}]
// The host wakes it on time. Messages wake it too (`status`, replies):
// then it checks on time with a timer instead.
void on_activated() override {
    if (status_.state != "watching") return;
    const std::int64_t left = next_check_ - now_ms();
    if (left > std::max<std::int64_t>(5, watch_.interval_ms / 2)) {
        (void)paglets::after_raw(left, "check", {});
        return;
    }
    check(0);
}
\end{lstlisting}
% /snippet

Note what the hook does not say: whether it was a message, a timer or the
wake-up that caused the activation. The \paglet{} works that out from its
own clock and state. Activation also happens without the \paglet{} having
asked for anything: after a restart of the host, and after a deactivation
through the runtime's API, the next delivery activates it the same way.
The image a deactivation stores is the same kind of image a move sends and
a checkpoint keeps, the linear memory and the exported mutable globals of
the instance, taken between calls, so there is no stack to save
(Section~\ref{sec:movement}).

\subsection{Moves: dispatching, arrival and refusal}\label{sec:lifecycle-moves}

\code{dispatch(destination)} asks for a move with a transfer ticket: a
host name or key ID, or a selector such as \code{label:linux},
\code{offer:<service>} or \code{any}, optionally followed by the options
\code{?retries=N} and \code{arrival=active|inactive}. It fails at once, with the
error as the result, when the host is not in a mesh
(\code{unsupported}), when the \paglet{} is not roaming (\code{denied}),
when another end operation is pending in this handler
(\code{bad\_state}), or while the \paglet{} is pinned to its host
(\code{pinned}). Otherwise the request is recorded and the handler goes
on. After it returns, the host calls \code{on\_dispatching} with the
destination, takes the image, and hands the image and the \paglet{}'s
travelling state (its capability table, pending requests, marks and
restart policy) to the mesh. From then until the destination has answered,
the \paglet{} is inactive here and messages for it are held.

Two outcomes exist. If the destination accepts the \paglet{}, it is
instantiated there from the image, and its first call on the new host is
\code{on\_arrived}, with \code{from}, the key ID of the host it left, and
\code{lost}, the capabilities that could not be re-created there. The held
messages follow it. No \code{on\_activated} precedes \code{on\_arrived}.
A ticket with \code{arrival=inactive} makes the \paglet{} wait on the new
host as an image until a message comes; then \code{on\_arrived} runs first,
followed by the message. If the destination refuses the \paglet{}, or
cannot be reached, nothing has happened to it: it is still on its host,
with the state the image holds, and it hears why through
\code{on\_move\_failed}. Because the \paglet{} was inactive while the
outcome was pending, that report activates it, so a refused move runs
\code{on\_activated} and then \code{on\_move\_failed}. The journey
example, which visits every host of the mesh in turn, continues from both
hooks with the same step (Listing~\ref{lst:lifecycle-journey-moves}):
\code{record\_and\_go\_on} notes the arrival in the journal and calls
\code{go\_on}; \code{on\_move\_failed} notes the host it could not reach
and calls the same \code{go\_on}, unless the unreachable host was home.

% snippet: cpp/examples/journey/journey.cpp#moves [caption={The journey's \code{on\_arrived} and \code{on\_move\_failed}},label={lst:lifecycle-journey-moves}]
\begin{lstlisting}[style=paglets-cpp,caption={The journey's \code{on\_arrived} and \code{on\_move\_failed} \src{cpp/examples/journey/journey.cpp}},label={lst:lifecycle-journey-moves}]
void on_arrived(const paglets::abi::ArrivedEvent&) override { record_and_go_on(); }

void on_move_failed(const paglets::abi::MoveFailed& f) override {
    if (journal_.state != "travelling") return;
    journal_.skipped.push_back(f.destination + ": " + f.reason);
    // Home out of reach: the journey ends where it is.
    if (f.destination == home_) {
        journal_.state = "failed";
        return;
    }
    go_on();  // the next host
}
\end{lstlisting}
% /snippet

Its \code{go\_on} shows the other kind of failure, the immediate one, where
\code{dispatch} itself returns an error and the \paglet{} tries the next
host in the same handler (Listing~\ref{lst:lifecycle-journey-go-on}).

% snippet: cpp/examples/journey/journey.cpp#go_on [float,caption={The journey's \code{go\_on}: a dispatch that fails at once is skipped in the same handler},label={lst:lifecycle-journey-go-on}]
\begin{lstlisting}[style=paglets-cpp,float,caption={The journey's \code{go\_on}: a dispatch that fails at once is skipped in the same handler \src{cpp/examples/journey/journey.cpp}},label={lst:lifecycle-journey-go-on}]
void go_on() {
    if (next_ >= itinerary_.size() && here_ == home_) {
        journal_.state = "home";  // nothing (more) to visit
        return;
    }
    std::string destination = next_ < itinerary_.size() ? itinerary_[next_++] : home_;
    left_ms_ = now_ms();
    if (auto moved = paglets::dispatch(destination); !moved) {
        if (destination == home_) {
            journal_.state = "failed";
            journal_.skipped.push_back("home: " + pt::error_text("dispatch", moved.error()));
            return;
        }
        journal_.skipped.push_back(destination + ": " + pt::error_text("dispatch", moved.error()));
        go_on();
    }
}
\end{lstlisting}
% /snippet

Two details of the window between \code{on\_dispatching} and the departure
are worth stating. A pin set while \code{on\_dispatching} runs wins: the
move is refused locally with the reason \code{pinned until}. (A pin
requested during the handler itself is refused with \code{bad\_state},
because a dispatch is pending.) And if the image cannot be taken, the
\paglet{} stays and is told so with the reason \code{no image}. A clone
for another host (\code{clone\_raw} with a destination) is handed to the
mesh the same way, but without \code{on\_dispatching}: its image is the
clone snapshot of step 1, the original keeps running, the clone's first
call on the destination is \code{on\_cloned}, and a refusal reaches the
original as \code{on\_move\_failed} with \code{clone} set to the clone's
ID. Section~\ref{sec:movement} describes what the mesh does between the
departure and the arrival.

\subsection{Reports instead of exceptions}\label{sec:lifecycle-reports}

A \paglet{} cannot catch an exception from the host, because nothing of the
host runs inside it. Failures that happen after a call returned are
reported as messages from the host instead, and the SDK delivers them as
hooks. There are three. \code{paglets.move\_failed}, described above.
\code{paglets.undelivered}: an asynchronous send or reply
(\code{SendOptions::async}, \code{reply\_async}) returned \code{ok} at
once, and the host could not deliver the message; the failure is reported
in a later handler, and the report names the message, the endpoint or
reply capability it went through, and the error the synchronous call
would have returned. Capabilities transferred with the message are gone,
as after a successful send, and a failed reply has answered the requester
\code{gone}. \code{paglets.recovered}, described next.

The reports share three properties. They carry no sender record, which is
how the SDK tells them from messages of the same name sent by a \paglet{}
(a send with a name under the reserved prefix \code{paglets.} is refused
by the host anyway). They are delivered at the highest message priority,
7, so they come before ordinary messages queued earlier, and in order
with replies, which use the same priority. And they are ordinary
deliveries: a report wakes an inactive \paglet{},
and \code{on\_message} never sees it. The defaults of
\code{on\_move\_failed} and \code{on\_undelivered} log a warning with the
destination or message name and the reason, so a \paglet{} that does not
override them still leaves a trace in the host log.

The synchronous failures remain results. Every SDK call that can fail
returns a \code{Result}, a \code{std::expected} with an ABI error code,
and a handler that returns a negative code for a request makes the host
answer the requester with that code.

\subsection{Disposal and failure}\label{sec:lifecycle-end}

\code{dispose} ends the \paglet{} after the handler: \code{on\_disposing}
runs, then the host answers every request still in its mailbox and every
reply capability it holds with \code{gone}, drops its capabilities,
removes its stored image and forgets it. Later sends to it fail with
\code{not\_found}. A \paglet{} that is inactive when the host disposes it
is activated first (\code{on\_activated}, then \code{on\_disposing}); one
that has not run yet gets \code{on\_created} first, because the host's
request queues behind it. A trap ends a \paglet{} as well, but as a
failure: an out-of-bounds access, \code{unreachable}, stack exhaustion, a
handler that exceeds its time budget (5\,s by default) or
\code{proc\_exit}. The host discards the instance, answers the requests in
its mailbox and the reply capabilities it holds with \code{failed}, and
does not run \code{on\_disposing}. This holds for handlers and for
\code{on\_activated} and \code{on\_deactivating}; a trap in
\code{on\_dispatching} is reported to the \paglet{} as a failed move
(reason \code{no image}), and a trap in \code{on\_disposing} is logged and
the \paglet{} ends as disposed. An operator's \code{terminate} (CLI and
web UI, admins only) ends a \paglet{} the same way as a trap, as failed and
without a hook, also while a handler runs. A trap is the \paglet{}'s own
fault, and it is not resumed from an earlier image; only a \paglet{} whose
worker process ended for another reason comes back from its last image. A
negative result from a hook, in contrast, is logged and changes nothing;
the SDK answers \code{malformed} when an event document does not decode,
and \code{not\_handled} for an event kind it does not know, which lets a
newer host add events without breaking older modules.

\subsection{Checkpoints and restarts}\label{sec:lifecycle-restart}

On a host with a state directory (every host started with \code{serve}),
a \paglet{} outlives the host process. The host stores its image after its first
handler and then at the checkpoint interval, 1\,s by default, whenever a
handler ends without a deactivation, move or disposal pending. After a
restart the host reads every record back, reschedules the timers, answers
the requests that were in flight with \code{timeout}, and activates each
\paglet{} at its next delivery, from the last image. A \paglet{} that was
between two checkpoints comes back in the state of the last image: what
it did since then is forgotten on its side, and the messages it handled
are not delivered again, because the mailbox is not part of the stored
record (the capability table, the pending requests and the timers are);
its effects on others, the messages it sent, remain. It may therefore do
the same work twice. ABI v1.2 adds two operations for \paglet{}s that need
more control than that, both as lifecycle operations next to
\code{dispose} and \code{dispatch}:

% snippet: cpp/common/include/paglets/abi.hpp#restart [caption={The restart policy and the recovery report},label={lst:lifecycle-restart}]
\begin{lstlisting}[style=paglets-cpp,caption={The restart policy and the recovery report \src{cpp/common/include/paglets/abi.hpp}},label={lst:lifecycle-restart}]
// v1.2: the restart policy. With `restart`, the host stores the paglet's
// images and brings it back from the last one after a restart (the
// default); without, the paglet ends with its host process. With
// `notify_recovered`, a paglet that came back receives `paglets.recovered`
// (Recovered) as its first message.
struct RestartArg {
    bool restart = true;
    bool notify_recovered = false;
};

// v1.2: payload of `paglets.recovered`.
inline constexpr std::string_view recovered_message = "paglets.recovered";
struct Recovered {
    std::int64_t image_ms = 0;      // when the image it came back from was stored (Unix milliseconds)
    std::int64_t restarted_ms = 0;  // when the host restarted (Unix milliseconds)
};
\end{lstlisting}
% /snippet

\code{checkpoint()} asks for an image right after the current handler,
before the next delivery. A \paglet{} calls it before an effect that must
not be repeated after a restart, such as sending a message that promises
work is done. The zombie pattern of Section~\ref{sec:zombies} relies on it:
when its protocol persists, the pattern calls \code{checkpoint()} and sends
that step's messages from its next handler, after the host stored the
image (durable before visible). Without a state directory,
\code{checkpoint()} returns \code{ok} and stores nothing; a \paglet{}
cannot tell the difference from its result.

\code{set\_restart(restart, notify\_recovered)} sets the policy.
\code{restart} is true by default. With it false, the \paglet{} is never
stored (an image stored earlier is removed right after the handler that
set the policy) and ends with its host process. With \code{notify\_recovered}, a \paglet{} that
came back receives \code{paglets.recovered} as a message, with the time
its image was stored and the time the host came back, so it can judge
what it missed and drop or redo work from before the restart. The
policy is kept in the \paglet{}'s record: clones inherit it, it travels
with the \paglet{}, and \code{self\_info} reports it. The exact order
after a restart with \code{notify\_recovered} is: \code{on\_activated},
then the \code{timeout} replies of the requests that were in flight, each
to its continuation, then \code{on\_recovered}, then the ordinary mail.
The replies and the report share priority 7 and the replies are queued
first. A \paglet{} that treats \code{on\_recovered} as its first chance to
reset its state must therefore expect those continuations to run before it,
on the state of the image. The zombie pattern's \code{on\_recovered}
invalidates its timers and deferred outputs, raises a generation counter
that stale continuations check, and re-enters its protocol in the
\code{recovering} role (Section~\ref{sec:zombies}).

\subsection{The ABI view}\label{sec:lifecycle-abi}

Underneath the hooks, the ABI between host and module has two entry points
for everything described above. \code{paglets\_on\_event(kind, ptr, len)}
receives the seven lifecycle events with a MessagePack document;
\code{paglets\_on\_message(ptr, len)} receives every message, with the
\code{Delivered} document of Section~\ref{sec:model}. The kinds, the
message kinds and the lifecycle operations are small integers
(Listing~\ref{lst:lifecycle-abi-kinds}).

% snippet: cpp/common/include/paglets/abi.hpp#events [float,caption={Event kinds, message kinds and lifecycle operations},label={lst:lifecycle-abi-kinds}]
\begin{lstlisting}[style=paglets-cpp,float,caption={Event kinds, message kinds and lifecycle operations \src{cpp/common/include/paglets/abi.hpp}},label={lst:lifecycle-abi-kinds}]
enum class EventKind : std::int32_t {
    created = 1,
    activated = 2,
    deactivating = 3,
    arrived = 4,
    cloned = 5,
    dispatching = 6,
    disposing = 7,
};

enum class MessageKind : std::int32_t { message = 0, request = 1, reply = 2, timer = 3 };

// v1.2: checkpoint (store an image right after this handler) and restart
// (whether the paglet comes back after its host restarts, RestartArg).
enum class LifecycleOp : std::int32_t { dispose = 1, deactivate = 2, clone = 3, dispatch = 4, checkpoint = 5, restart = 6 };
\end{lstlisting}
% /snippet

The event documents are maps with string keys, decoded by hand-written
code that both the host and the guest share; a decoder skips keys it does
not know, which is how documents gain fields within a major version:

% snippet: cpp/common/include/paglets/abi.hpp#event-documents [caption={The event documents},label={lst:lifecycle-abi-documents}]
\begin{lstlisting}[style=paglets-cpp,caption={The event documents \src{cpp/common/include/paglets/abi.hpp}},label={lst:lifecycle-abi-documents}]
// Event documents. `created` and `cloned` share the args/caps fields.
struct StartEvent {
    std::vector<std::uint8_t> args;
    std::vector<std::int32_t> caps;
    std::optional<std::string> original;  // cloned only
};

struct ArrivedEvent {
    std::string from;
    std::vector<std::string> lost;
};

struct DispatchingEvent {
    std::string destination;
};
\end{lstlisting}
% /snippet

The SDK's export decodes the document for the kind and calls the hook.
This is all the dispatch there is; a module written without the SDK
implements the same switch (Listing~\ref{lst:lifecycle-sdk-on-event}).

% snippet: cpp/sdk/src/paglet.cpp#on_event [float,caption={The SDK's \code{paglets\_on\_event}},label={lst:lifecycle-sdk-on-event}]
\begin{lstlisting}[style=paglets-cpp,float,caption={The SDK's \code{paglets\_on\_event} \src{cpp/sdk/src/paglet.cpp}},label={lst:lifecycle-sdk-on-event}]
switch (static_cast<abi::EventKind>(kind)) {
    case abi::EventKind::created:
    case abi::EventKind::cloned: {
        abi::StartEvent e;
        if (!abi::decode(view(ptr, len), e)) return abi::malformed;
        paglets::Started s = started_from(e);
        if (static_cast<abi::EventKind>(kind) == abi::EventKind::created) {
            p.on_created(s);
        } else {
            p.on_cloned(s);
        }
        return abi::handled;
    }
    case abi::EventKind::activated: p.on_activated(); return abi::handled;
    case abi::EventKind::deactivating: p.on_deactivating(); return abi::handled;
    case abi::EventKind::arrived: {
        abi::ArrivedEvent e;
        if (!abi::decode(view(ptr, len), e)) return abi::malformed;
        p.on_arrived(e);
        return abi::handled;
    }
    case abi::EventKind::dispatching: {
        abi::DispatchingEvent e;
        if (!abi::decode(view(ptr, len), e)) return abi::malformed;
        p.on_dispatching(e);
        return abi::handled;
    }
    case abi::EventKind::disposing: p.on_disposing(); return abi::handled;
}
return abi::not_handled;
\end{lstlisting}
% /snippet

Reports arrive through \code{paglets\_on\_message}, after the replies with
a continuation have been routed and before \code{on\_message}
(Listing~\ref{lst:lifecycle-sdk-reports}).

% snippet: cpp/sdk/src/paglet.cpp#reports [float,caption={The SDK turns the host's reports into hooks},label={lst:lifecycle-sdk-reports}]
\begin{lstlisting}[style=paglets-cpp,float,caption={The SDK turns the host's reports into hooks \src{cpp/sdk/src/paglet.cpp}},label={lst:lifecycle-sdk-reports}]
// Reports of asynchronous sends and replies come from the host (no sender).
if (m.kind() == abi::MessageKind::message && m.name() == abi::move_failed_message && !m.sender()) {
    abi::MoveFailed f;
    if (!m.decode(f)) return abi::malformed;
    paglets::detail::paglet().on_move_failed(f);
    return abi::handled;
}
if (m.kind() == abi::MessageKind::message && m.name() == abi::recovered_message && !m.sender()) {
    abi::Recovered e;
    if (!m.decode(e)) return abi::malformed;
    paglets::detail::paglet().on_recovered(e);
    return abi::handled;
}
if (m.kind() == abi::MessageKind::message && m.name() == abi::undelivered_message && !m.sender()) {
    abi::Undelivered u;
    if (!m.decode(u)) return abi::malformed;
    paglets::detail::paglet().on_undelivered(u);
    return abi::handled;
}
\end{lstlisting}
% /snippet

Three things the host does not guarantee: it does not say why a
\paglet{} was activated, it does not let a hook refuse a transition, and
it does not deliver \code{activated} before \code{arrived} or
\code{cloned}, because the image was taken on the other side of a
transition and the new instance is not a wake-up of an old one.
